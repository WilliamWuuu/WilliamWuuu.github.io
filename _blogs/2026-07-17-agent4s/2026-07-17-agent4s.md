This blog is basically a review of [FunSearch](https://www.nature.com/articles/s41586-023-06924-6), [AlphaEvolve](https://arxiv.org/abs/2506.13131) and [Co-Scientist](https://www.nature.com/articles/s41586-026-10644-y).

Suppose we had an AI system capable of formulating scientific hypotheses, reading the literature, writing simulation code, designing experiments, and analyzing results. Then we can simply input a research problem or hypothesis, hoping it will provide a one-shot solution or answer.

But would merely doing that be sufficient to produce genuinely novel scientific discoveries?

The problem is that scientific discovery rarely emerges from a single "generation". It typically involves an iterative cycle:

- propose candidates (solutions, hypothesis, ...)
- evaluate and test
- identify problems
- revise
- test again

This has the same basic structure as evolutionary search. So it's believed that AI for scientific discovery is not about having a more powerful model directly produce answers; rather, it is about organizing LLMs or LLM-based agents, tools, evaluators, external memory, and resource scheduling into a system capable of conducting long-horizon search, accumulating knowledge, and continuously improving itself.

## From Optimization to Search

Assume finding the solution to a scientific problem can be modeled as:

$$
\begin{equation}
x^*=\underset{x\in\mathcal{X}}{\operatorname{argmax}}\,R(x),
\end{equation}
$$

where $\mathcal{X}$ represents the set of all candidate solutions, and $R(x)$ is the evaluation function used to measure the quality of the solution.

From an optimization perspective, this is a search problem: we aim to find a program that maximizes the evaluation function within a vast search space $\mathcal{X}$. However, unlike neural network parameter optimization, the solution space is typically discrete and structurally complex. Take programs for example, modifying a program does not correspond to a small movement in a continuous space:

From

```Python
def heuristic(x):
    return x.size
```

to

```Python
def heuristic(x):
    return x.size ** 2
```

though the code change is minimal, the resulting behavior may change significantly. Therefore, program spaces generally do not possess exploitable continuous structures, and the search process cannot be directly guided by local information such as gradients.

However, for any candidate program, we can typically:

1. Generate the program;
2. Execute the program;
3. Determine whether it satisfies the constraints;
4. Compute its performance score based on task-specific metrics.

This type of property is usually summarized as _hard to solve but easy to evaluate_. 

A natural approach to this kind of search problem is to continuously generate new candidate programs, use the evaluation function to select better candidates, and repeat this process. For example, suppose a machine has chosen an number between 1 and 100. We first make an arbitrary guess (generate) and receive feedback indicating whether the guess is too high or too low (evaluate). Based on this feedback, we iteratively narrow the search range and make new guesses until we identify the correct number.

### Evolutionary Search

Here I want to introduce evolutionary search, since it's the fundemental idea behind the evolutionary components following. Code is implemented in [Google Colab](https://colab.research.google.com/drive/1b2uWTHz5WAmlZxKavGNDAJYGaLAUYnc_?usp=sharing).

Evolutionary search is a population-based stochastic search method that maintains a set of candidate solutions and continuously generates better candidate solutions through mutation, recombination, evaluation, and selection.

{% include widgets/blog_image.html src="evolutionary_search.png" caption="Picture 1: Evolutionary Search." %}

Let the population at generation $t$ be:

$$
P_t=\{x_t^{(1)}, x_t^{(2)}, \dots, x_t^{(N)}\}
$$

where each candidate $x_t^{(i)}$ is called an **individual** in the population.

**Step 1**: Select several individuals from the current population that are worth further exploration:

$$
\begin{equation}
x_\text{parent}\sim \mathrm{Select}(P_t,R)
\end{equation}
$$

For multiple individuals in a population, if we want to use an algorithm to obtain the best candidates, we need a metric to evaluate the quality of each individual. We call this metric **fitness**, which corresponds to the evaluation function $R$ in the example above.

A common selection strategy is **tournament selection**. Specifically, we randomly sample $k$ individuals from the population and choose the best individual with probability $p$, the second best with probability $p*(1-p)$, the third best with probability $p*((1-p)^2)$, so on.

Then we just call this strategy multiple times to gain the parent individuals. The reason we cannot simply select only a single individual is due to the **exploration–exploitation trade-off**:

- **Exploitation:** If the selection pressure is too strong, and we only select the best individuals for reproduction, the entire search process degenerates into a single greedy trajectory. Although this leads to faster convergence, population diversity quickly disappears, making the search prone to getting trapped in local optima.
- **Exploration:** If the selection pressure is too weak, we maintain rich population diversity, but a large amount of computational budget is spent evaluating low-quality candidates. As a result, performance improvement becomes slow.

**Step 2**: **Mutation**. We usually refer to the program itself as **genotype**, while the behavior or output produced by executing the program is called **phenotype**. Mutation introduces perturbations to the genotype of the candidate obtained from the previous step:

$$
\begin{equation}
x_\text{child}=M(x_\text{parent})
\end{equation}
$$

For example, in LLM-based program search, this step may involve modifying expressions in an algorithm, rewriting the logic of key functions, fixing bugs, or making other program-level changes.

When generating offspring from a parent, we sometimes want to combine the strengths of multiple candidate individuals. The process of combining information from multiple parents to produce offspring is called **crossover**. In LLM-based program search, this can be implemented by placing two candidate programs into the context and allowing the LLM to compare them and incorporate desirable components from both.

Step 3: Evaluate the mutated candidate:

$$
\begin{equation}
s_\text{child}=R(x_\text{child})
\end{equation}
$$

Here, the object being evaluated is the **phenotype** of the offspring.

Step 4: Select survivors from the parents and offspring to form the next generation:

$$
\begin{equation}
P_{t+1}=\mathrm{Survive}(P_t\cup C_t,f)
\end{equation}
$$

Here, we allow two generations of populations to compete with each other, ensuring that the best candidate individuals are not lost. This mechanism is known as **elitism**.

## FunSearch

In **FunSearch**, the search target is a function $f$, which generates solutions through the function:

$$
\begin{equation}
x=f(z)
\end{equation}
$$

where $z$ is the problem input. Therefore, the optimization objective (Eq. (1)) becomes:

$$
\begin{equation}
f^*=\underset{f\in\mathcal{P}}{\operatorname{argmax}}\, R(f)
\end{equation}
$$

where $\mathcal{P}$ is the program space.

FunSearch typically does not allow the agent to modify the entire software system. Instead, it only modifies a key function within the system. Let the entire solving program be denoted as $S[f]$, where $S$ is a fixed program framework (also called the **skeleton**); $f$ is the key function that FunSearch is allowed to modify; and $S[f]$ represents the complete program obtained by inserting function $f$ into the skeleton $S$.

In programming, we usually use a set of test cases to determine whether a program is functionally correct. Let the evaluation set be:

$$
D=\{z_1,z_2,\dots,z_r\}
$$

where each $z_i$ is an evaluation input. For a candidate function $f$, the complete program receives a score on input $z_i$:

$$
\begin{equation}
e_i(f)=E(S[f],z_i)
\end{equation}
$$

where $E$ is the evaluator, and $e_i(f)$ is the score of function $f$ on the $i$-th input. The scores of the candidate program across different inputs are combined through an aggregate function $A$ as:

$$
\begin{equation}
J(f)=A(e_1(f),e_2(f),\dots,e_r(f))
\end{equation}
$$

At each iteration, FunSearch builds a prompt by combining several programs sampled from the programs database (favouring high-scoring ones). The prompt is then fed to the pretrained LLM and new programs are created. Newly created programs are then scored and stored in the programs database (if correct), thus closing the loop. ### Specification

The **Specification** provides a complete definition of the modifiable function interface, the fixed program skeleton, the evaluation methodology, and the tools available to the system. It includes:

- The name of the modifiable function;
- The input and output types;
- A description of the function;
- The fixed solving framework;
- The evaluator;
- The initial function implementation;
- The libraries or auxiliary functions that can be used.

### Evaluator

The **Evaluator** is responsible for assessing candidate programs from three perspectives:

- **Syntactic validity:** whether the code can be successfully parsed by the compiler.
- **Execution validity:** whether the program terminates within the specified time limit, stays within the memory constraints, and does not raise runtime exceptions.
- **Output validity and quality:** whether the output satisfies the problem constraints and what quality score the output achieves.

### Program Database

The **Program Database** is a persistent storage component that maintains valid candidate programs, their scores on different inputs, their aggregated performance scores, and the populations they belong to. It serves as an external memory system: information stored outside the model parameters that can be accessed and updated by the search process.

#### Islands

In details, the database is viewed as a population, divided into multiple relatively independent subpopulations (islands). Assume that $m$ islands are initialized:

$$
I_1,I_2,...,I_m.
$$

Given the initial program $f_0$, each island starts from the same program:

$$
\begin{equation}
I_j=\{f_0\},\quad j=1,\dots,m.
\end{equation}
$$

After initialization, each island independently evolves its own subpopulation.

Whenever a prompt needs to be constructed:

1. Select an island $I_j$ uniformly at random;
2. Select parent programs only from this island;
3. Generate a new program from the selected parents;
4. After evaluation, store the new program back into the same island.

Every certain period of time, the best program from each island is compared:

$$
\begin{equation}
B_j=\max_{f\in I_j}J(f)
\end{equation}
$$

The replacement process is then performed as follows:

1. Identify the bottom half of islands according to their best program scores;
2. Clear these islands;
3. For each cleared island, randomly select a surviving island;
4. Copy the best program from the surviving island into the cleared island;
5. Restart the search process from this copied program.

#### Signature Clustering

An island can be further divided into several clusters. A **cluster** is a group of objects that are considered similar according to a given similarity criterion. In FunSearch, programs with identical signatures are assigned to the same cluster.

The **signature** of a candidate program $f$ is a vector consisting of its individual scores across $r$ evaluation inputs:

$$
\sigma(f) = (e_1(f),e_2(f),\dots,e_r(f))
$$

After selecting an island as said earlier, FunSearch first samples a cluster and then samples a program from within that cluster. Let the signature of cluster $C_i$ be:

$$
s_i=(s_{i}^{(1)},s_i^{(2)},\dots,s_i^{(r)})
$$

FunSearch applies **Boltzmann Selection** to determine the probability of selecting each cluster:

$$
\begin{equation}
P(C_i)=\frac{\exp(\bar{s}_i/T)}{\sum_{j}\exp(\bar{s}_j/T)}
\end{equation}
$$

where $\bar{s}_i=A(s_{i}^{(1)},s_i^{(2)},\dots,s_i^{(r)})$ represents the aggregated quality of cluster $C_i$; $T$ is the temperature parameter, which controls the concentration of the probability distribution: A larger $T$ produces a probability distribution closer to uniform sampling (**exploration**), while a smaller $T$ concentrates the probability mass on high-performing candidates (**exploitation**).

The temperature can be periodically adjusted according to the number of programs in an island:

$$
\begin{equation}
T_\text{cluster}=T_0\left(1-\frac{n\,\mathrm{mod}\,N}{N}\right)
\end{equation}
$$

where: $n$ is the current number of programs in the island; $N$ is the predefined cycle length; $T_0$ is the initial temperature.

After selecting a cluster, FunSearch favors sampling shorter programs. Let the length of a program be $L(f)$, measured by the number of characters. The preference can be conceptualized as:

$$
\begin{equation}
P(f\vert C_i) \propto \exp\left(-\frac{\tilde{L}(f)}{T_\text{program}}\right)
\end{equation}
$$

where $\tilde{L}(f)$ is the normalized program length; $T_\text{program}$ is the temperature parameter controlling the preference for shorter programs.

### Prompt Builder

FunSearch does not simply provide the LLM with the single “current best program.” Instead, it selects multiple programs from the database and constructs a prompt that presents them in an ordered sequence of improvements. This approach is known as **best-shot prompting**, where the model is guided by a set of progressively improved examples rather than a single solution.

Best-shot prompting selects high-scoring programs from historical candidates, arranges these programs in ascending order according to their scores, and instructs the LLM to generate the next improved version.

Assume that the selected two programs satisfy:

$$
\begin{equation}
J(f_a)<J(f_b)
\end{equation}
$$

The constructed prompt can be represented as:

```Python
def priority_v0(x):
    # lower score implementation
    ...

def priority_v1(x):
    # higher score implementation
    ...

def priority_v2(x):
    # TODO
```

If only a single best-performing program is provided, the LLM receives just a static point $f_{\text{best}}$. However, if two programs with different performance levels are provided, the LLM can also infer an implicit improvement trajectory:

$$
\begin{equation}
f_\text{low}\rightarrow f_\text{high}
\end{equation}
$$

This provides the LLM with semantic information about a possible direction for further improvement.

## AlphaEvolve

AlphaEvolve can be viewed as a large-scale and generalized extension of FunSearch.

| FunSearch | AlphaEvolve |
| --- | --- |
| Modify a key function | Modify multiple code blocks |
| Single score | Multi-metric evaluation |
| Complete function generation | Structured code patching |
| Fixed prompts | Rich history, feedback, and domain context |
| Single-layer evaluation | Evaluation cascade |

AlphaEvolve targets problems with machine-gradeable solution, which can be automatically evaluated by computer programs and assigned one or more quantitative metrics. Given a candidate program $P$, the evaluation function can be represented as:

$$
E(P)=(m_1(P),m_2(P),\dots,m_d(P))
$$

where $E$ is the evaluation function, $m_i(P)$ represents the $i$-th evaluation metric, and $d$ is the number of metrics.

The overall architecture of AlphaEvolve can be summarized as integration of the following components:

- **Task Specification:** defines which parts of the code can evolve and how candidates are evaluated;
- **Prompt Sampler:** constructs prompts from historical programs and contextual information;
- **LLM Ensemble:** generates candidate code modifications;
- **Patch Applier:** applies modifications to the existing code through patches;
- **Evaluators:** execute and rate candidate programs;
- **Evolutionary Database:** stores results and selects future parent candidates.

{% include widgets/blog_image.html src="AlphaEvolve.png" caption="Picture 5: Expanded view of the AlphaEvolve discovery process. The user provides an initial program (with components to evolve marked), evaluation code, and optional configurations. AlphaEvolve then initiates an evolutionary loop. The Prompt sampler uses programs from the Program database to construct rich prompts. Given these prompts, the LLMs generate code modifications (diffs), which are applied to create new programs. These are then scored by Evaluators, and promising solutions are registered back into the Program database (Section 2.5), driving the iterative discovery of better and better programs." %}

### Task Specification

#### Evaluation Function

AlphaEvolve requires users to provide an evaluation function that maps candidate programs to measurable metrics:

```Python
def evaluate(eval_inputs) -> dict[str, float]:
    ...
    return metrics
```

The returned metrics define the performance of each candidate and determine whether it should survive in the evolutionary process.

#### Evolution Blocks

AlphaEvolve allows users to explicitly specify modifiable regions using special markers:

```Python
# EVOLVE-BLOCK-START

def optimizer():
    ...

def loss_function():
    ...

# EVOLVE-BLOCK-END
```

The remaining code stays unchanged and serves as the fixed program skeleton.

Compared with FunSearch, which usually evolves only a single function, AlphaEvolve supports multiple **evolution blocks**. These blocks can contain classes, functions, configurations, or even complete algorithmic components.

### Prompt Sampling

The prompts used by AlphaEvolve contain substantially more information than those in FunSearch. A typical prompt can be expressed as:

$$
p=\mathrm{Compose}(\text{instructions},\text{context},\text{prior programs},\text{current program},\text{evaluation feedback})
$$

where $\mathrm{Compose}$ represents the process of combining multiple information sources into a single input for the LLM.

**Prior programs** are previously generated candidates stored in the evolutionary database. Similar to FunSearch's best-shot prompting, AlphaEvolve uses historical candidates as examples to guide future generations. However, AlphaEvolve can provide much richer information, including:

- multiple previous programs;
- complete code implementations;
- multiple evaluation metrics for each candidate;
- execution outputs;
- natural-language feedback;
- domain-specific knowledge.

**Explicit context** refers to additional information provided by users and directly inserted into the prompt. It may include:

- problem definitions;
- mathematical formulations;
- code snippets;
- engineering constraints;
- related research papers;
- API documentation;
- known failed approaches;
- hardware specifications.

This allows the LLM to reason not only from previous solutions but also from external domain knowledge.

### Patch-Based Evolution

A key difference between FunSearch and AlphaEvolve is the way code modifications are represented.

For a small function, rewriting the entire function is often acceptable. However, when evolving a codebase containing hundreds or thousands of lines, asking an LLM to rewrite the entire file introduces several issues:

- Correct existing code may be accidentally deleted;
- Unrelated modifications may be introduced;
- Token consumption becomes significantly higher;
- It becomes difficult to determine which change caused performance improvement;
- Repeated iterations may lead to **code drift**, where the program gradually deviates from its original structure and accumulates unnecessary or inconsistent changes.

To solve this problem, AlphaEvolve typically requires the LLM to output a **diff**, which specifies exactly which existing code should be replaced and what new code should be inserted.

A patch has a structure similar to:

```
<<<<<<< SEARCH
return optax.adam(learning_rate)
=======
return optax.adamw(
    learning_rate,
    weight_decay=1e-4,
)
>>>>>>> REPLACE
```

where:

- The `SEARCH` section must exactly match the corresponding code in the current program;
- The `REPLACE` section contains the new implementation.

Patch-based evolution enables precise, localized modifications while preserving the overall software structure.

### LLM Ensemble

Instead of relying on a single language model, AlphaEvolve can combine multiple models or model configurations to generate candidate solutions.

For example, using Gemini 2.0 Flash and Gemini 2.0 Pro, the overall generation distribution can be represented as:

$$
\begin{equation}
q(P^\prime)=\lambda q_\text{Flash}(P^\prime)+(1-\lambda)q_\text{Pro}(P^\prime)
\end{equation}
$$

where:

- $q_\text{Flash}$ and $q_\text{Pro}$ represent the candidate distributions generated by the two models;
- $\lambda\in[0,1]$ controls their relative contribution.

The ensemble approach allows different models to contribute different exploration behaviors and improves the diversity of generated candidates.

### Evaluation Cascade

Large-scale code evolution requires efficient evaluation. Running expensive evaluations on every generated program would quickly become computationally infeasible.

AlphaEvolve therefore introduces an **evaluation cascade**, where candidates pass through multiple evaluation stages with gradually increasing costs.

A typical evaluation pipeline may contain:

```
Stage 0: Syntax and import checking
Stage 1: Small-scale input testing
Stage 2: Limited random seeds
Stage 3: Full evaluation dataset
Stage 4: Large-scale parallel experiments
Stage 5: Strict correctness verification
```

Formally, assume the cascade contains $K$ evaluation stages:

$$
E_1,E_2,\dots,E_K
$$

with increasing costs:

$$
\begin{equation}
c_1<c_2<\cdots<c_K
\end{equation}
$$

Each stage has a passing threshold $\tau_k$. A candidate program $P$ proceeds to the next stage only if:

$$
\begin{equation}
E_k(P)\geq\tau_k
\end{equation}
$$

This design filters out low-quality candidates early and reserves expensive computation for promising solutions.

### Meta-Prompt Evolution

A further extension of AlphaEvolve is the evolution of the prompts themselves.

A **meta-prompt** is a prompt designed to generate, modify, or select other prompts. Rather than evolving only candidate programs, AlphaEvolve can also evolve the strategies used to guide program generation:

- The LLM can propose new instructions and contextual information through additional prompt-generation steps;
- These meta-prompts are stored in an independent database;
- Meta-prompts can evolve together with candidate programs.

This process can be represented using two archives:

$$
\begin{align*}
\mathcal{A}_P &= \{\text{candidate programs}\}\\
\mathcal{A}_M &= \{\text{candidate meta-prompts}\}
\end{align*}
$$

The search process therefore evolves both the solutions and the mechanisms used to discover solutions.

## Co-Scientist

Systems such as FunSearch and AlphaEvolve typically search over programs. Co-Scientist, by contrast, searches over scientific hypotheses. Its objective is not merely to generate plausible-sounding ideas, but to assess their credibility and research value through critique, comparison, literature review, and eventually experimentation.

This difference is fundamental. A program can usually be executed, and its output can often be evaluated against a clear specification. Scientific hypotheses rarely offer such an inexpensive and deterministic evaluation function.

Several difficulties make scientific hypotheses substantially harder to evolve than programs:

1. **Correctness is generally unknown before experimentation**, while experimental feedback is expensive and slow.
2. **Novelty depends on the broader scientific literature**, rather than on the hypothesis alone.
3. **Importance requires expert value judgments**, including judgments about scientific significance and potential impact.
4. **Testability depends on available laboratory conditions**, instruments, samples, budgets, and ethical constraints.
5. **Hypothesis quality is inherently multidimensional** and often cannot be compressed into a single scalar score.

The central question behind Co-Scientist is therefore:

> How can a system generate, critique, compare, select, and iteratively improve a large population of scientific hypotheses when no cheap and deterministic evaluator is available?

### What Counts as a Scientific Hypothesis?

A **scientific hypothesis** is a proposition about a phenomenon, mechanism, or causal relationship that can, at least in principle, be supported or contradicted by evidence.

A rigorous hypothesis should specify at least:

- the object of study;
- the predicted relationship;
- a possible mechanism;
- the conditions under which the claim applies;
- the expected observable outcomes;
- the observations that could count against it.

This last requirement is closely related to **falsifiability**: there must be some possible observation or experimental result that would indicate that the hypothesis is false.

A hypothesis is distinct from a **research proposal**. A research proposal is a broader research plan organized around one or more hypotheses. It usually includes background, rationale, experimental design, expected results, risks, and alternative strategies.

An **experimental protocol** goes one step further. It translates the proposal into concrete, executable laboratory procedures, including materials, variables, controls, measurement methods, and analysis procedures.

Co-Scientist is intended to help move ideas along this continuum:

$$
\text{Scientific hypothesis}
\rightarrow
\text{Research proposal}
\rightarrow
\text{Experimental protocol}
\rightarrow
\text{Empirical evidence}
$$

### Quality Criteria

A useful output from Co-Scientist should satisfy five criteria.

- Alignment: The output must directly address the scientist’s research objective, preferences, and constraints.
- Plausibility: The hypothesis must not contain obvious errors relative to current knowledge. When it conflicts with established research, the conflict should be stated explicitly and explained. Plausibility does not mean that the hypothesis is correct. It means only that, given existing knowledge \(K\), its conditional probability is not obviously close to zero: $P(H\mid K)\not\approx 0$.
- Novelty: The hypothesis should not merely restate a published conclusion. It should introduce a relationship, mechanism, prediction, or experimental direction that has not already been explicitly proposed or validated.
- Testability: The hypothesis must be convertible into empirical observations or experiments under the scientist’s stated technical, financial, resource, and ethical constraints.
- Safety: The output must not facilitate unsafe, unethical, or clearly harmful research.

### Scientific Discovery as Population-Based Search

Co-Scientist approximates scientific discovery as a long-running search over a population of hypotheses:

$$
\mathcal{H}_t=\{H_1,H_2,\ldots,H_{n_t}\}
$$

Here, $\mathcal{H}_t$ denotes the set of hypotheses maintained at time $t$.

The system repeatedly executes a cycle of:

$$
\text{Generate}
\rightarrow
\text{Reflect}
\rightarrow
\text{Compare}
\rightarrow
\text{Rank}
\rightarrow
\text{Evolve}
\rightarrow
\text{Generate again}
$$

This formulation resembles evolutionary search, but the objects being evolved are semantic scientific claims rather than executable programs. Their fitness is not measured by a single objective function. Instead, it is estimated through a collection of specialized reviewers, comparisons, external evidence sources, and human feedback.

| Search function | Co-Scientist component |
|---|---|
| Produce initial candidates | Generation Agent |
| Check errors and novelty | Reflection Agent |
| Compare candidates pairwise | Ranking Agent |
| Maintain relative ordering | Elo tournament |
| Identify duplicates and nearby directions | Proximity Agent |
| Improve and combine candidates | Evolution Agent |
| Summarize systematic evaluation failures | Meta-review Agent |
| Allocate computational resources | Supervisor Agent |
| Preserve long-term state | Context Memory |
| Provide reliable external information | Web search, databases, specialized models, and human experts |

### System Components

#### Natural-Language Interaction

Scientists interact with the system through a natural-language interface. They can:

- define a research objective;
- specify constraints;
- provide background literature;
- revise the objective;
- evaluate system-generated hypotheses;
- submit their own hypotheses;
- instruct the system to explore a particular direction.

The interface matters because scientific objectives are rarely static. A scientist may change priorities after inspecting an intermediate hypothesis, discovering an experimental limitation, or identifying a promising mechanism.

#### Asynchronous Task Execution

The agents do not have to wait for a strict global iteration to finish. Each agent can operate independently once its dependencies are satisfied.

For example:

- the Generation Agent may be producing new hypotheses;
- the Reflection Agent may simultaneously review earlier hypotheses;
- the Ranking Agent may compare hypotheses whose reviews have been completed;
- the Proximity Agent may update the similarity graph;
- the Evolution Agent may refine the current highest-ranked candidates.

This asynchronous design makes the system closer to a distributed research organization than to a single sequential language-model prompt.

#### Specialized Agents

The system includes several specialized agents:

- Generation;
- Reflection;
- Ranking;
- Proximity;
- Evolution;
- Meta-review.

These agents are coordinated by a central Supervisor Agent.

#### Persistent Context Memory

A persistent external memory stores research objectives, hypotheses, reviews, rankings, statistics, and human feedback across agent calls and iterative search cycles.

Let the memory state at time $t$ be $M_t$. It is updated as follows:

$$
\begin{equation}
M_{t+1}
=
\mathrm{Update}
\left(
M_t,
\text{new hypotheses},
\text{reviews},
\text{matches},
\text{meta-reviews}
\right)
\end{equation}
$$

Persistent memory prevents each agent from reconstructing the entire research context from scratch. It also allows the system to recover from execution failures without restarting the scientific search from the beginning.

### Research Plan Configuration

The user’s input may range from a single-sentence research question to a large research package containing:

- a long natural-language document;
- tens of thousands of tokens of context;
- hundreds of research-paper PDFs;
- private experimental data;
- laboratory-specific technical limitations;
- a required output format.

The **research plan configuration** is the structured task definition extracted by the Supervisor from this input.

It can include:

- the research topic;
- the primary objective;
- known evidence;
- required properties of acceptable hypotheses;
- experimental constraints;
- whether novelty is mandatory;
- permitted tools;
- evaluation criteria;
- output requirements;
- safety restrictions.

The same configuration is reused by different agents throughout the search process. This reduces the risk that each agent will independently interpret the research task in a different way.

### Supervisor Agent

The **Supervisor Agent** is the control component responsible for managing the task queue, assigning workers, tracking system statistics, and deciding where additional computational resources should be allocated.

#### Task Queue

A task queue stores work that is waiting to be executed. A task can be represented as:

$$
T=
(\text{agent type},\text{action},\text{input IDs},\text{priority})
$$

For example:

```text
(Reflection, full_review, hypothesis_17, high)
(Ranking, compare, [hypothesis_8, hypothesis_17], medium)
(Evolution, combine, [hypothesis_4, hypothesis_8], medium)
```

A **worker** is a computational unit that retrieves a task from the queue and executes the corresponding agent logic.

The Supervisor adjusts the sampling weights of different task types according to statistics such as:

- the number of hypotheses generated;
- the number of hypotheses awaiting review;
- the number of tournament matches played by each hypothesis;
- the maturity of the tournament;
- the relative success rates of Generation and Evolution;
- whether the system lacks sufficiently diverse research directions;
- whether the highest-ranked hypotheses are still improving.

#### Terminal States

A **terminal state** is reached when the system satisfies a predefined stopping condition and no longer allocates new tasks.

Possible stopping conditions include:

- the hypothesis population reaches a maximum size;
- the average number of matches per hypothesis reaches a limit;
- the computational budget is exhausted;
- the scientist manually stops the process;
- the Supervisor determines that the task-specific termination condition has been met.

### Generation Agent

The Generation Agent is responsible for opening up the hypothesis space rather than merely optimizing the current best candidate.

#### Literature-Grounded Generation

A literature-grounded generation process may includes: The agent iteratively searches the web, retrieves and reads relevant research articles, learns about topics and grounds its reasoning by summarizing previous work
and building a knowledge base of scientific facts. It then builds on this summary to generate hypotheses and research plans.

The example prompt provided by the paper:

```text
You are an expert tasked with formulating a novel and robust hypothesis to address the following objective.

Describe the proposed hypothesis in detail, including specific entities,
mechanisms, and anticipated outcomes.

This description is intended for an audience of domain experts.

You have conducted a thorough review of relevant literature and developed a logical framework for addressing the objective. The articles consulted, along with your analytical reasoning, are provided below.

Goal: {goal}

Criteria for a strong hypothesis:
{preferences}

Existing hypothesis (if applicable):
{source_hypothesis}

{instructions}

Literature review and analytical rationale (chronologically ordered, beginning with the most recent analysis):

{articles_with_reasoning}

Proposed hypothesis (detailed description for domain experts):
```

#### Simulated Scientific Debate

The model can simulate researchers who hold different positions. These roles propose claims, challenge one another, respond to criticism, and eventually produce a revised hypothesis.

The example prompt provided by the paper:

```text
You are an expert participating in a collaborative discourse concerning the generation of a {idea_attributes} hypothesis. You will engage in a simulated discussion with other experts. The overarching objective of this discourse is to collaboratively develop a novel and robust {idea_attributes} hypothesis.

Goal: {goal}

Criteria for a high-quality hypothesis:
{preferences}

Instructions:
{instructions}

Review Overview:
{reviews_overview}

Procedure:

Initial contribution (if initiating the discussion):
Propose three distinct {idea_attributes} hypotheses.

Subsequent contributions (continuing the discussion):
* Pose clarifying questions if ambiguities or uncertainties arise.
* Critically evaluate the hypotheses proposed thus far, addressing the following aspects:
    - Adherence to {idea_attributes} criteria.
	- Utility and practicality.
	- Level of detail and specificity.
* Identify any weaknesses or potential limitations.
* Propose concrete improvements and refinements to address identified weaknesses.
* Conclude your response with a refined iteration of the hypothesis.

General guidelines:
* Exhibit boldness and creativity in your contributions.
* Maintain a helpful and collaborative approach.
* Prioritize the generation of a high-quality {idea_attributes} hypothesis.

Termination condition:
When sufficient discussion has transpired (typically 3-5 conversational turns, with a maximum of 10 turns) and all relevant questions and points have been thoroughly addressed and clarified, conclude the process by writing "HYPOTHESIS" (in all capital letters) followed by a concise and self-contained exposition of the finalized idea.

#BEGIN TRANSCRIPT#
{transcript}
#END TRANSCRIPT#

Your Turn:
```

#### Layered Hypothesis Construction

The Generation Agent can decompose a complete hypothesis into intermediate assumptions or necessary conditions $A_1,A_2,\ldots,A_k$ through conditional reasoning hops.

For example:

$$
\begin{align*}
A_1 &: \text{The target is abnormally active in a subtype of AML} \\
A_2 &: \text{The drug inhibits the target at an achievable concentration} \\
A_3 &: \text{The inhibition does not cause comparable damage to normal cells}
\end{align*}
$$

These assumptions or subassumptions are aggregated into complete hypotheses subsequently.

#### Research Expansion

The Generation Agent can also inspect existing hypotheses, meta-review feedback, and the current research overview to identify regions of the hypothesis space that remain unexplored.

It summarizes and categorizes generated hypotheses so that scientists can browse the population efficiently rather than reading every proposal in full.

### Reflection Agent

The Reflection Agent functions as a multilayer peer-review system.

#### Initial Review

The initial review does not use external search tools. It performs a rapid check of whether a hypothesis:

- addresses the research objective;
- contains obvious factual errors;
- lacks basic plausibility;
- merely repeats common knowledge;
- creates safety or ethical concerns.

The purpose is to filter a large number of low-quality candidates at low cost.

#### Full Review

A full review can use web search, academic literature retrieval, or private materials supplied by the scientist.

It examines:

- support from the literature;
- factual correctness;
- novelty;
- underlying assumptions;
- the reasoning chain;
- experimental feasibility.

Evaluating novelty requires more than searching for similar keywords. The agent must first summarize which parts of the hypothesis are already known and then determine whether the remaining relationship, mechanism, or experimental proposal is genuinely new.

#### Deep Verification Review

A deep verification review decomposes the hypothesis into elementary premises and checks each premise independently of the original narrative.

Suppose:

$$
\begin{equation}
H=A_1\wedge A_2\wedge\cdots\wedge A_k
\end{equation}
$$

The Reflection Agent can further decompose each premise:

$$
\begin{equation}
A_i=A_{i1}\wedge A_{i2}\wedge\cdots
\end{equation}
$$

It then determines whether an incorrect premise is central or peripheral.

- If a core premise is false, the hypothesis may need to be eliminated.
- If a nonessential detail is wrong, the Evolution Agent may be able to repair it.

#### Decontextualization

**Decontextualization** temporarily removes the persuasive narrative surrounding a hypothesis and evaluates each premise as an independent proposition.

This is useful because a coherent scientific story can make weak assumptions appear more convincing than they would in isolation.

#### Observation Review

An observation review asks whether the hypothesis can explain unusual, rare, neglected, or previously unexplained experimental observations.

A hypothesis becomes more valuable when it explains these observations better than existing theories. In practice, however, this form of review may frequently fail to uncover meaningful new evidence.

A **long-tail observation** is an experimental phenomenon that appears infrequently and is not the primary conclusion of a study, but may nevertheless contain important information about an underlying mechanism.

#### Simulation Review

In a simulation review, the language model steps through the proposed mechanism or experimental process and searches for possible failure modes.

This procedure relies on an important assumption: that a frontier language model contains an internal world model capable of approximating at least some relevant scientific processes.

Such simulation cannot replace real experimentation, but it may expose contradictions, missing variables, or unrealistic experimental assumptions.

#### Recurrent Tournament Review

The Reflection Agent can adjust future review priorities based on problems that repeatedly appear in previous reviews and tournament debates.

Human expert reviews can also be incorporated into the system and used to guide subsequent evaluations.

### Ranking Agent

#### Pairwise Comparison

Instead of asking for an absolute score, the Ranking Agent compares two candidates $H_i$ and $H_j$ and decides which is better.

Pairwise judgments may be easier than absolute evaluations because the reviewer only needs to identify relative advantages. However, pairwise preferences are not necessarily transitive:

$$
\begin{equation}
H_1\succ H_2,\qquad
H_2\succ H_3,\qquad
H_3\succ H_1
\end{equation}
$$

Such cycles can arise when hypotheses have different strengths. One may be more novel, another more plausible, and a third easier to test.

#### Tournament-Based Ranking

A **tournament** establishes a relative ordering through a large number of pairwise matches among candidates.

Every new hypothesis begins with an Elo rating of $R_i=1200$. Under the standard Elo model, the expected probability that $H_i$ defeats $H_j$ is:

$$
\begin{equation}
p_i=
\frac{1}
{1+10^{(R_j-R_i)/400}}
\end{equation}
$$

After the match, the rating is updated according to:

$$
\begin{equation}
R_i^{\prime}
=
R_i+K(S_i-p_i)
\end{equation}
$$

where:

- $S_i=1$ represents a win;
- $S_i=0.5$ represents a draw;
- $S_i=0$ represents a loss;
- $K$ controls how strongly a single match affects the rating.

Elo does not prove that the highest-rated hypothesis is scientifically correct. It provides a continuously updated estimate of relative preference under the system’s current evaluators and comparison criteria.

#### Debate for High-Ranking Hypotheses

Comparisons between high-ranking hypotheses use a more expensive, multiround debate process:

1. analyze the strengths of $H_i$;
2. analyze the strengths of $H_j$;
3. criticize both hypotheses;
4. respond to those criticisms;
5. compare novelty, correctness, and testability;
6. select a winner and explain the decision.

Lower-ranked hypotheses can be evaluated using cheaper, single-round comparisons.

#### Positional Bias

**Positional bias** occurs when the decision depends on the order in which candidates appear in the prompt.

A debate-oriented prompt can improve ranking accuracy and reduce positional bias compared with a simple one-pass comparison.

#### Match Selection

The Ranking Agent prioritizes comparisons involving:

- hypotheses identified as similar by the Proximity Agent;
- newly introduced hypotheses;
- currently high-ranking hypotheses.

Comparing nearby hypotheses is especially informative. When two hypotheses pursue similar directions, the evaluator can ask which version is more rigorous, better supported, or easier to test.

Comparing completely different hypotheses often requires subjective trade-offs among unrelated scientific goals.

### Proximity Agent

**Proximity** measures the semantic similarity of two hypotheses in terms of research objects, mechanisms, evidence, or experimental design.

The system represents these relationships as a **proximity graph**:

$$
G=(V,E)
$$

where:

$$
V=\mathcal{H}
$$

is the hypothesis population. If $H_i$ and $H_j$ are sufficiently similar, the graph contains an edge:

$$
(i,j)\in E
$$

The edge may have a similarity weight $w_{ij}$.

The proximity graph can be used to:

- cluster related ideas;
- identify duplicates;
- select informative tournament opponents;
- visualize the hypothesis space;
- help scientists locate related research directions;
- preserve multiple distinct regions of exploration.

This last function is particularly important. Without explicit diversity management, an evolutionary system may gradually collapse onto a narrow family of similar high-scoring ideas.

### Evolution Agent

The Evolution Agent produces new candidates from existing high-ranking hypotheses:

$$
\begin{equation}
\mathcal{H}_{t+1}
=
\mathcal{H}_t\cup\{H_{\text{new}}\}
\end{equation}
$$

Its strategies include the following.

#### Grounded Enhancement

The agent identifies weaknesses in a hypothesis, formulates search questions, retrieves relevant literature, and fills gaps in evidence or reasoning.

#### Consistency, Utility, and Feasibility Improvements

The agent repairs problems such as:

- internal contradictions;
- invalid assumptions;
- unrealistic experiments;
- unavailable samples;
- excessive costs;
- unmeasurable endpoints.

#### Inspiration

The agent extracts useful structures from one or more strong hypotheses and generates new hypotheses inspired by them.

#### Semantic Crossover

The agent can combine the strengths of several high-ranking hypotheses:

$$
\begin{equation}
H_{\text{new}}
=
\mathrm{Combine}(H_i,H_j,\ldots)
\end{equation}
$$

This resembles crossover in evolutionary algorithms, but there is no fixed syntactic rule for recombination. The operation occurs at the semantic level.

#### Simplification

A complicated hypothesis can be rewritten using fewer variables, a clearer mechanism, and a more direct validation strategy.

Simplification is not merely stylistic. A simpler hypothesis may require fewer experiments, produce more interpretable evidence, and expose its falsification conditions more clearly.

#### Out-of-the-Box Exploration

The agent can deliberately move away from currently dominant high-ranking directions and search for different mechanisms or representations.

This prevents the hypothesis population from becoming progressively homogeneous.

### Meta-Review Agent

The Meta-review Agent reviews the evaluation process itself.

A **meta-review** extracts recurring errors, omissions, and useful evaluation rules from multiple reviews and tournament debates.

For example, suppose many proposed treatments for amyotrophic lateral sclerosis fail to consider whether the compound can cross the blood–brain barrier. The Meta-review Agent may derive the following general rule:

> Future reviews of central nervous system drug candidates must explicitly evaluate blood–brain barrier permeability.

That rule can then be incorporated into subsequent Reflection, Generation, or Evolution prompts.

The Generation Agent uses meta-review feedback selectively rather than treating every criticism as a mandatory constraint. Otherwise, all new hypotheses could become restricted by the same review pattern, reducing diversity and discouraging unconventional ideas.

At the end of a computational run, the Meta-review Agent can synthesize the highest-ranking candidates into a research overview containing:

- the major current hypothesis families;
- the importance of each direction;
- supporting evidence and unresolved disputes;
- major knowledge gaps;
- executable experiments;
- possible future research paths.

This overview can be supplied to the Generation Agent again, initiating another exploration cycle.

### Constrained Decoding

**Constrained decoding** restricts model outputs to a predefined format or grammar during generation.

For example, the system may require every hypothesis to contain fields such as:

```text
Research object:
Predicted relationship:
Proposed mechanism:
Boundary conditions:
Observable outcomes:
Falsification criteria:
Supporting evidence:
Experimental design:
Safety considerations:
```

Structured output improves interoperability among agents. It also makes hypotheses easier to compare, review, store, and convert into experimental proposals.

### From Language-Based Evaluation to an Experimental Loop

The architecture described so far relies heavily on language-based evaluation. Agents generate arguments, retrieve evidence, critique assumptions, conduct debates, and assign relative rankings.

This approach is useful, but it has a fundamental limitation: linguistic evaluation is still only a proxy for scientific truth.

A high Elo score means that a hypothesis consistently defeats other hypotheses under the current comparison process. It does not mean that the hypothesis is empirically correct.

The long-term objective should therefore be to connect the hypothesis population to an experimental feedback loop:

$$
\text{Hypothesis generation}
\rightarrow
\text{Review and ranking}
\rightarrow
\text{Experimental design}
\rightarrow
\text{Experiment execution}
\rightarrow
\text{Data analysis}
\rightarrow
\text{Hypothesis update}
$$

In such a system, experimental results become a source of evaluator signals.

Suppose an experiment $E$ produces observation $O$. The belief associated with a hypothesis can be updated from:

$$
P(H\mid K)
$$

to:

$$
P(H\mid K,O,E)
$$

The experimental result may:

- strengthen a hypothesis;
- weaken it;
- falsify a core premise;
- reveal a missing condition;
- distinguish between two similarly ranked hypotheses;
- produce a new long-tail observation;
- generate an entirely new research direction.

The feedback should update more than the individual hypothesis. It can also update:

- Reflection criteria;
- ranking preferences;
- proximity relationships;
- assumptions about experimental feasibility;
- meta-review rules;
- future generation strategies.

The resulting system is no longer merely a collection of language agents discussing scientific ideas. It becomes a closed-loop scientific search process in which language models help manage the hypothesis space, while experiments provide the ultimate empirical constraint.

The complete loop can be summarized as:

$$
\boxed{
\text{Generate}
\rightarrow
\text{Critique}
\rightarrow
\text{Compare}
\rightarrow
\text{Rank}
\rightarrow
\text{Evolve}
\rightarrow
\text{Experiment}
\rightarrow
\text{Update}
}
$$

Programs are comparatively easy to evolve because they can often be executed against a deterministic evaluator. Scientific hypotheses lack that convenience. Their evaluation requires literature, expert judgment, multidimensional comparison, experimental feasibility analysis, and eventually real-world evidence.

Co-Scientist addresses this problem by replacing a single evaluator with an organized ecosystem of evaluators: specialized agents, pairwise tournaments, persistent memory, external tools, human experts, and experimental feedback.

The system’s central contribution is therefore not simply automated hypothesis generation. It is an architecture for maintaining and improving a population of scientific hypotheses under uncertainty, incomplete knowledge, and expensive empirical validation.
